The desktop widget, end to end

A small Electron app that renders the dashboard's account rail as its own frameless window — nothing more. It doesn't call any API itself; it reads the same docs/data.json the dashboard reads, straight off disk, and shares its rail-rendering code with the dashboard via one file.

01 Data flow

The widget has no backend of its own. On launch, its main process starts a tiny local HTTP server that serves two separate roots on one port, then just points a browser window at it.

No bundled dataThe widget doesn't ship a copy of data.json and doesn't call YouTube/Instagram itself — it points its server's /docs/ route straight at the dashboard repo's real docs/ folder on disk. Whatever the Python pipeline last wrote there is what the widget shows, with zero syncing logic.

02 main.js — the Electron main process

Everything the widget needs at the OS level lives in one file: the local server, the window, and settings persistence.

desktop/main.js134 lines
  • DOCS_DIR is a hardcoded absolute path to the dashboard repo's docs/ folder. This is a personal, single-machine tool — no portability concerns, so a real path beats a config file nobody would ever touch.
  • startServer() — one http.createServer() routes on URL prefix: a request starting with /docs/ serves from DOCS_DIR (stripping the prefix), everything else serves from WIDGET_DIR (i.e. desktop/ itself, via __dirname). serveFrom() resolves the final path and checks it still starts with the intended root before reading, so a crafted ../../ in a URL can't escape either folder.
  • Chose a real local server over loading files with a bare file:// URL because Chromium's fetch() behavior for local JSON over file:// is inconsistent — a server makes the widget's data.json fetch behave identically to how it behaves on GitHub Pages.
  • loadSettings() / saveSettings() — a small JSON file in Electron's own userData directory, merged over hardcoded defaults so an old settings file missing a newer key (like panelOpacity) doesn't crash on load.
  • createWindow() — frame: false, transparent: true, resizable: true, sized 320×560, show: false until ready-to-show fires (avoids a blank-white flash on launch). alwaysOnTop is seeded from the persisted setting so the pin toggle survives a restart.
  • Five ipcMain handlers: open-external (fire-and-forget, used by every account click and the header's dashboard link), plus a get/set pair each for alwaysOnTop and panelOpacity — the "get" side lets the renderer ask for the current value on load without main having to push anything.
Trickiest bug this sessionwin.setWindowOpenHandler() doesn't exist — that method lives on win.webContents, not the BrowserWindow itself. Wrong call site, right-looking code; Electron's docs list it under WebContents but it's easy to reach for it off the window instance by habit.

03 preload.js — the only bridge in or out

The renderer (widget.html/js) runs with nodeIntegration: false and contextIsolation: true — no Node or Electron API is reachable from its JS except what this file explicitly exposes.

desktop/preload.js9 lines

contextBridge.exposeInMainWorld('electronAPI', …) hands the renderer exactly four functions, each a thin wrapper over one ipcRenderer call: openExternal, getAlwaysOnTop / setAlwaysOnTop, getPanelOpacity / setPanelOpacity. Nothing else — no raw ipcRenderer, no filesystem, no require() — crosses into the page's JS.

04 widget.html / widget.js — the renderer

The entire window is the rail card — one .rail-inner div, no other page chrome.

desktop/widget.html44 lines
  • Same markup skeleton as the dashboard's rail (.rail-brand, .rail-label, #channelTabs, .rail-foot) minus the "All accounts" entry — there's no dashboard view here to aggregate into.
  • Loads /docs/styles.css (the dashboard's real stylesheet, over the network route from main.js) before its own widget.css, so widget-specific rules can override the shared ones by cascade order alone.
  • Two extra controls the dashboard doesn't have: a pin button (#pinToggle) and an opacity slider (#opacitySlider), both described below.
desktop/widget.js70 lines
  • init() — fetches /docs/data.json, renders every channel via the shared railItemHtml(), then wires each button's click to window.electronAPI.openExternal(channel.url) instead of filtering a view.
  • initPinToggle() — reads the persisted always-on-top value on load, toggles aria-pressed and calls setAlwaysOnTop() on click.
  • initOpacitySlider() — same read-on-load / write-on-change pattern, but purely visual: it sets a CSS custom property (--panel-bg-alpha) directly on .rail-inner, no window-level API involved.
  • initDashboardLink() — the "Furadi" wordmark in the header is a button, not a static label; clicking it opens the live GitHub Pages dashboard externally, same IPC path as an account click.

05 Sharing code with the dashboard

Rather than duplicate the rail's markup logic for a second UI, it was extracted once so both consumers stay visually identical by construction.

docs/rail.js84 lines · shared, not desktop-only

Plain classic script (no ES modules — matches how the rest of this project's frontend is written), loaded before both app.js (dashboard) and widget.js (widget). Exports onto window implicitly: IG_ACCENT, fmtInt, escapeHtml, isIG, isTraffic, accentOf, accentVarsStyle, sparklinePath, MAIL_ICON_PATH, and railItemHtml() itself.

  • The dashboard's buildRail() (in app.js) calls railItemHtml() once per channel and appends its own "All accounts" button and filter-click wiring on top — the widget just calls railItemHtml() directly and wires a different click behavior. Same output markup either way.
  • The animated sparkline (a bright band that sweeps along each trend line, masked to the line's exact shape) lives in railItemHtml() too, so both surfaces animate identically for free.
Why extract itBefore this, the rail's render function lived only inside app.js. Duplicating ~40 lines into the widget would have meant two copies to keep in sync by hand every time the rail's look changed — one file, one visual source of truth, instead.

06 Frameless, frosted, resizable

Three window-level design decisions, each with a reason it's not the more obvious default.

DecisionWhy not the obvious alternative
Tinted transparency, not true blur-behindA real "blur whatever's behind the window" effect needs an undocumented Windows compositor API. A community package (electron-acrylic-window) wraps it, but that API has shifted across Windows updates before with no guarantee of a timely fix — not worth the fragility for a personal tool. .rail-inner's background is a plain rgba() fill with a user-controlled alpha instead.
No title bar, but still a normal taskbar windowWindows shows Restore/Move/Size/Minimize/Maximize/Close on any taskbar icon's right-click menu regardless of frame — so dropping the title bar doesn't cost window controls. The whole panel is the drag handle instead (-webkit-app-region: drag, with buttons/sliders inside it marked no-drag so they stay clickable).
Not always-on-top by defaultA "normal" window that can be covered by other windows was the explicit ask — always-on-top is opt-in via the pin toggle, not the default.
desktop/icon.svg → icon.icobrand mark

The same dark-square/orange-uptrend mark used for the dashboard's favicon, redrawn at 256×256 with Pillow (no SVG rasterizer was available in this environment) and exported as a multi-resolution .ico for the taskbar icon and the installer.

Settings persistenceuserData/settings.json

Both the pin state and the opacity slider write through ipcMain to a small JSON file in Electron's per-app userData folder — survives reinstalls of the app itself since it's outside the install directory.

07 Packaging

electron-builder produces a one-click NSIS installer for Windows — the only platform this personal tool targets.

desktop/package.jsonbuild config
  • npm start → electron . for local dev; npm run dist → electron-builder for the real installer.
  • No code signing — an unsigned installer trips Windows SmartScreen once ("More info → Run anyway"), which is normal and acceptable for a tool that never leaves this machine. A signing certificate would cost money purely to silence a warning nobody but the author ever sees.
  • desktop/node_modules and desktop/dist are both gitignored — Electron's own install is ~150–200MB (it bundles Chromium) and the installer itself is another ~78MB, neither belongs in source control.

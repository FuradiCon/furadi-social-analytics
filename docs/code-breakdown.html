02 Automation

One workflow does the whole job — no separate deploy step, since the commit itself is the deploy on GitHub Pages.

.github/workflows/update-dashboard.yml 50 lines
  • Cron */20 * * * * plus a manual workflow_dispatch escape hatch.
  • concurrency.cancel-in-progress: false — a slow run finishes rather than getting killed by the next scheduled tick, which would otherwise race the commit.
  • Five secrets get written to disk as credential files at job start (three YouTube token groups, the Instagram token, and its client secret) — nothing is baked into the repo.
  • pytest runs before the build step — a red test suite blocks a bad data.json from ever being generated.
  • Commit step diffs first (git diff --cached --quiet ||) so a no-op fetch (nothing changed upstream) doesn't create an empty commit every 20 minutes.
Why this mattersThe pipeline can lose one channel entirely (expired token, dead API) and the workflow still goes green and still ships an update — see build() below.

03 Data pipeline — scripts/

Five small, independently-testable modules. build_data.py is the only one that knows about all of them.

scripts/build_data.py132 lines · orchestrator

Calls the three fetchers for every configured channel, catching exceptions per channel rather than globally:

  • build() — loops CHANNEL_CFGS (the 4 YouTube channels), plus one call each for Steadfast Counter and Instagram. Each is wrapped in its own try/except; a single failure just logs and moves on.
  • Only exits non-zero (fails CI) if every source failed — any_success gates it. One dead token shouldn't redden the whole pipeline run.
  • download_instagram_thumbnails() — Instagram's media URLs are short-lived signed links, so thumbnails get pulled down once into docs/assets/ and referenced by local path from then on; a 403 on one thumbnail is caught, the partial file is deleted so the next run retries it, and the post just ships without an image rather than sinking the batch.
  • Final write is data.json.tmp → os.replace() — an atomic rename, so a page load can never see a half-written file mid-build.
scripts/youtube_pipeline.py198 lines
  • get_credentials() — refreshes an expired token silently; only falls back to the interactive OAuth flow (prompt="select_account", forces the account picker so a logged-in browser can't silently reuse the wrong Google account) when there's no valid refresh token at all.
  • Pulls the YouTube Analytics report (views, watch time, subs, likes/comments/shares by day) for the current window and the prior window, for the KPI delta chips.
  • fetch_recent_comments() + thread_needs_reply() — walks each comment thread's replies and checks whether the channel owner was the last to reply; that's what drives the "awaiting reply" badge and the favicon glow.
  • Top-video thumbnails link straight to YouTube's own CDN URL rather than being embedded — avoids ballooning data.json (and every 20-minute commit) by hundreds of KB.
scripts/instagram_pipeline.py104 lines
  • get_access_token() — refreshes the long-lived token once it's within 3 days of expiry, then writes the new token back as a GitHub secret via gh secret set so the next CI run picks it up. The credential file on disk is otherwise disposable.
  • Splits fetched media into current/prior 28-day windows by timestamp for the same delta-chip treatment as YouTube.
  • No OAuth dance here — Instagram's long-lived tokens just get refreshed in place, no browser flow.
scripts/steadfast_pipeline.py74 lines

Not a social account — reads accumulated page-view traffic for a separate site ("Scattered to Steadfast") straight off its own repo's raw traffic.json/usage.json files on GitHub, rather than hitting any live API.

  • Usage/cost data is fetched separately and allowed to fail soft to {} — traffic numbers matter more than the cost figure, so a broken usage.json shouldn't blank the traffic chart.
  • Rendered first in the rail (prepended in build()) so it sits above the YouTube channels.
scripts/datawindow.py50 lines · shared helpers
  • window_dates() — a fixed 28-day window ending 2 days back (PROCESSING_LAG_DAYS), since YouTube Analytics data isn't final for the most recent day or two.
  • rows_from_response() / totals_from_rows() — reshape the Analytics API's column-header + row-array format into named dicts, and roll them up into period totals for the delta chips.

A parallel tests/ directory (5 files, one per pipeline module) runs via pytest as the CI gate before build_data.py ever executes.

04 Frontend shell — docs/

Static site, zero build step. index.html is mostly empty containers; app.js fills every one of them from data.json at runtime.

docs/index.html180 lines
  • The channel rail (#channelTabs) is the signature nav element — each account renders as its own mini terrain-sparkline, built entirely in JS.
  • Chart/table containers exist as empty <div>/<table> shells with fixed IDs — app.js owns 100% of what goes inside.
  • A <canvas id="bgCanvas"> sits behind everything for the ambient background (see below); a <noscript> fallback swaps in a static network-art image if JS never runs.
docs/styles.css686 lines
  • Dark instrument-panel theme: graphite ground, glass-translucent card surfaces, five saturated brand hues reserved strictly for plotted marks (bars, sparkline strokes, chips) — never for glow or for small text sitting directly on the page ground.
  • Per-channel color is a CSS custom-property swap: applyAccent() in JS rewrites --accent / --accent-strong / --accent-soft on the root, so one stylesheet serves every channel's distinct identity.
  • Semantic up/down colors (--up / --down) are deliberately kept outside the five brand hues, so a subscriber-loss day doesn't accidentally borrow a channel's own brand color.

06 Background renderers

Three swappable full-canvas backgrounds behind a shared manager (setActiveBackground(), persisted to localStorage), each exposing the same tiny { id, start, stop, resize } interface.

particlesRenderer~60 lines

Drifting dots, linked by a faint line when two fall within range. Count scales with canvas area, capped 36–90.

matrixRenderer~80 lines

Classic flat falling-code rain. Column speed and the black-fade trail are both normalized to real elapsed time (dt), not frame count, so a capped or high-refresh display doesn't change perceived speed.

matrix2Renderer~300 lines · this session's build

A perspective hallway of falling code converging on a square door panel — floor and ceiling march through depth, walls cascade top-to-bottom, everything squashed flat against its own surface (floor/ceiling squash vertically, walls squash horizontally — a Star Wars crawl effect via ctx.setTransform).

  • Depth-bucketed + size-quantized draw order avoids per-glyph ctx.font reassignment, one of canvas's most expensive operations at scale.
  • An ALPHA_MIN cutoff skips both the bucket and the glyph-selection/projection work for any trail glyph too faint to see — checked before the expensive part, not after.
  • Render loop capped to 60fps with motion normalized by dt, so the cap changes cost, never perceived speed.
  • Floor/ceiling/wall vertical projection deliberately shares the width-based scale formula (not height-based) so all three surfaces converge exactly on the door's edges.
Why it's split outBy far the heaviest of the three — thousands of fillText calls/frame — so it carries all the latency-specific work: frame capping, alpha culling, and hoisting per-frame closures out of the draw loop.
